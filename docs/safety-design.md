# 안전 설계 4원칙

> 운영 자동화에서 진짜 위험은 **자동화가 안 되는 것**이 아니라 **자동화가 잘못 실행되는 것**이다.
> 사람은 실수하면 하나를 틀리지만, 스크립트는 실수하면 전부를 틀린다.

비개발자가 자동화를 맡을 때 조직이 가장 걱정하는 것은 "만들 수 있느냐"가 아니라 **"사고를 안 낼 수 있느냐"** 다.
그래서 나는 기능보다 안전장치를 먼저 설계했다.

이 4원칙은 일반론이 아니라 **운영에서 반복 관찰된 실패 유형에서 역산**한 것이다.
유형 자체는 [조용한 실패 5유형 카탈로그](silent-failure-patterns.md)에 따로 정리해 뒀고,
아래 각 원칙에 **어떤 유형을 막으려고 만든 것인지**를 붙였다. 원칙이 먼저 있고 사례를 끼운 것이 아니라 순서가 그 반대다.

<br>

## 원칙 1 — 되돌릴 수 없으면 실행하지 않는다

**역산한 유형** · [유형 4 조용한 값 리셋 · 유형 5 자기 손상](silent-failure-patterns.md) — 둘 다 *돌아갈 원본*이 없으면 탐지해도 복구가 안 된다.

**롤백 경로를 먼저 확보하지 않은 실행은 시작 자체를 막는다.**

```
쓰기 전:  현재값 전체를 스냅샷으로 저장
실행 시:  스냅샷에 대상이 없으면 → 중단 (진행하지 않음)
종료 시:  복원 1회 실행으로 일괄 원복
```

**왜 이렇게까지 하는가** — 대형 변경은 되돌릴 시점에 담당자가 이미 지쳐 있고, 대상이 수십 건이면 반드시 몇 개를 빠뜨린다.
원복을 사람의 기억력에 맡기면 실패한다.
그리고 **스냅샷에 없는 항목은 복원 불가로 직결된다** — 백업 범위가 곧 복원 가능 범위이므로, 백업 여부를 규율이 아니라 **실행 전 가드**로 넣었다.

> 부수 효과 하나 — 스냅샷이 쌓이면 그 자체가 변경 이력이 된다. "언제부터 이 값이었나"를 물었을 때 답할 수 있다.

<br>

## 원칙 2 — 읽기와 쓰기를 분리하고, 읽기를 기본값으로 둔다

**역산한 유형** · [유형 4 조용한 값 리셋 · 유형 5 자기 손상](silent-failure-patterns.md) — 결함처럼 보이는 것이 의도된 설정일 수 있고(4), 멱등하지 않은 자동 수정은 실행할수록 상태를 나쁘게 만든다(5).

**감사·조회 도구는 코드 수준에서 쓰기 권한을 갖지 않는다.**

```
감사 도구        →  읽기 전용. 쓰기 0건이 설계 조건
실행 도구        →  dry-run 이 기본값. 실행은 명시적 플래그
파괴적 명령      →  차단 목록으로 원천 봉쇄
운영 DB 접근     →  기본 읽기 전용, 쓰기는 승인 후
```

**왜 이렇게까지 하는가** — 조사하다가 고치고 싶어지는 순간이 반드시 온다. 그때 도구에 쓰기 권한이 있으면 검증 없이 고치게 된다.
감사 결과는 **먼저 보고하고 나중에 조치**해야 한다. 결함처럼 보이는 것이 의도된 설정인 경우가 실제로 있기 때문이다.

<br>

## 원칙 3 — `200 OK` 를 반영으로 믿지 않는다

**역산한 유형** · [유형 4 조용한 값 리셋](silent-failure-patterns.md) — 절차를 정상적으로 밟았는데 값이 초기화되는 경우, 응답만 보면 성공으로 보인다.

**쓰기 후 독립 경로로 다시 조회해서 확인한다.**

```
1. 쓰기 요청 전송
2. 응답 200 수신          ← 여기서 멈추면 안 된다
3. 독립 재조회(read-back) 로 실제 값 확인
4. 고객이 보는 화면에서 최종 확인   ← 캐시 계층이 다르다
```

**왜 이렇게까지 하는가** — 관리자 화면과 실제 고객 화면이 다르게 보이는 경우가 있다. 캐시 계층이 다르기 때문이다.
API가 성공을 반환했는데 고객 화면에는 옛 값이 남아 있으면, 검증했다고 믿은 채로 사고가 진행된다.
**"반영됐다"의 정의를 고객 화면 기준으로** 잡고 나서야 검증이 검증이 되었다.

<br>

## 원칙 4 — 판단을 위임할 때는 롤아웃을 통제한다

**역산한 유형** · [유형 3 무증상 미수행](silent-failure-patterns.md) — 관찰 기간 없이 켜면 *0건과 급증의 정상 범위*를 모른 채 자동 판단을 맡기게 된다.

**되돌릴 수 없는 종류의 판단은 관찰 기간을 먼저 갖는다.**

```
1주차:  dry-run 기본값으로 배포 — 코드는 돌지만 아무것도 바꾸지 않는다
        알림만 받으며 정책의 정확도를 측정
2주차:  오탐 표본을 검토하고 규칙 보정
전환:   기본값을 뒤집어 활성화
상시:   일일 처리 한도 · 후보 급증 시 자동 차단 · 연속 실패 시 중단 · 비운영 환경 dry-run 강제
```

**왜 이렇게까지 하는가** — 정책 판단을 코드로 옮기는 순간, 틀리면 **되돌릴 수 없는 종류의 실수**가 된다.
처리 기준일(cutoff)을 안 걸면 켜는 순간 과거 수만 건이 일괄 처리된다. 이건 롤백이 있어도 이미 늦다.

<br>

## 종합 — 안전장치가 곧 포트폴리오다

| 원칙 | 막는 사고 유형 | 역산한 조용한 실패 유형 |
|---|---|---|
| 롤백 우선 | 종료 후 원복 누락 → 잘못된 값이 계속 노출 | 유형 4 · 5 |
| 읽기 기본 | 검증 없는 조치 → 의도된 설정을 결함으로 오인해 훼손 | 유형 4 · 5 |
| 재조회 검증 | 반영됐다고 믿은 채 진행 → 고객 화면만 옛 값 | 유형 4 |
| 롤아웃 통제 | 정책 오류의 일괄 적용 → 되돌릴 수 없는 대량 처리 | 유형 3 |

이 네 가지는 기능 목록에는 안 들어간다. 그런데 **실무에서 자동화를 맡길 수 있느냐**를 가르는 건 정확히 여기다.

> **두 유형이 남는다** — [유형 1 스케줄러 무응답 · 유형 2 만료](silent-failure-patterns.md)는 이 4원칙으로 막히지 않는다.
> 둘 다 *실행 방식*의 문제가 아니라 **실행 여부와 기한**의 문제여서, 원칙이 아니라 별도 장치로 처리한다 —
> 유형 1은 하트비트 감시([케이스 03](../cases/03-silent-failure-detection.md)), 유형 2는 만료 대장과 사전 통보.
> 원칙이 유형 전부를 덮지 않는다는 사실도 결과의 일부다. 덮는다고 적으면 그때부터 원칙이 아니라 구호다.
