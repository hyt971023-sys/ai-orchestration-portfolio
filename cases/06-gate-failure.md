# 케이스 06 — 내가 만든 안전장치가 실패했다

> 유출을 막으려고 만든 검사 게이트가, 막아야 할 것을 담은 채 **“전 항목 통과”를 출력하고 있었다**

**증명하는 역량** · 자기 안전장치를 적대적으로 검증하고, 결과에 따라 **기준 자체를 폐기**

<br>

## 이 케이스를 쓰는 이유

앞의 다섯 건은 제가 무엇을 만들었는지에 대한 기록입니다.
이 한 건은 **제가 만든 것이 실패한 기록**입니다.

이 저장소를 공개하기 전, 유일한 방어선이 구조적으로 무력화돼 있었습니다.
발견한 방법과 고친 방법이 앞의 다섯 건보다 더 실무에 가깝다고 생각해서 남깁니다.

<br>

## 문제

공개 전 검사 게이트를 만들었습니다. 저장소 전체를 훑어 **가리기로 한 문자열이 남아 있으면 커밋을 막는** 스크립트입니다.

쓸모 있게 만들려면 “무엇을 가릴 것인가”를 알려줘야 합니다.
그래서 **회사명·브랜드·상품명·업무 계정을 정규식에 직접 적었습니다.**

```bash
# 게이트 안에 있던 코드 (개념)
check "식별자" '<회사명>|<브랜드>|<상품명들>|<업무계정>'
```

두 가지가 동시에 잘못됐습니다.

### ① 금지어 목록이 곧 정답표가 됐다

가려야 할 것 전부가 **한 줄에 파이프로 정렬돼** 있었습니다.
저장소의 다른 파일은 전부 잘 정제돼 있었는데, **유출을 막는 파일 하나가 완전한 목록**이 됐습니다.
추론도 필요 없습니다. 복사해서 검색창에 넣으면 끝입니다.

### ② 게이트가 자기 자신을 검사에서 제외했다

```bash
hits=$(grep ... | grep -v 'redaction-gate.sh')   # ← 자기 자신 제외
```

처음에는 합리적으로 보였습니다. 게이트 안에 정규식 패턴이 있으니 자기가 자기를 잡을 테니까요.
결과는 **저장소에서 유일하게 기밀을 담은 파일이 영원히 검사 대상 밖**이 된 것이었습니다.

실행하면 이렇게 나왔습니다.

```
✅ 회사·브랜드 식별자
✅ 시스템 좌표
...
✅ 전 항목 통과          ← 회사명을 담은 채로
```

CI도 초록불이었습니다. **잘못된 확신까지 자동화**돼 있었습니다.

> 지금은 CI 가 게이트를 **양성 대조**로 검증합니다 — 카나리 문자열을 저장소에 심으면 실패하고,
> 빼면 통과하는지. 여기에 재발 방지 검사를 붙였습니다 — **규칙 파일이 없을 때 실제로 실패하는지**,
> **이름을 바꿔 넣은 규칙 파일도 걸리는지**, **작업 트리에서 지우고 히스토리에만 남은 문자열도 잡는지.**
> 카나리는 실행할 때 만듭니다. 워크플로 파일에 적어두면 그 문자열이 저장소 안에 남아
> 카나리를 빼도 계속 적중하고, 그러면 시험이 게이트를 검증하지 못합니다.

<br>

## 어떻게 발견했나

읽어서 찾은 게 아닙니다. **적대적 테스트로 찾았습니다.**

이 저장소의 맥락을 전혀 모르는 검증자 4명에게 저장소만 주고 임무를 줬습니다.

> **“이 저장소만 보고 작성자가 다니는 회사를 특정하라.”**

각각 다른 각도를 배정했습니다.

| 각도 | 접근 |
|---|---|
| 검색 역추적 | 저장소 문구·수치를 그대로 웹 검색 |
| 업종 추론 | 상품군·시장 구성·규모로 후보 좁히기 |
| 코드 흔적 | 주석·픽스처·커밋 메타데이터·CI 설정 |
| 법무 관점 | 회사가 문제 삼을 근거가 되는 서술 |

**4명 전원이 회사를 특정했습니다.** 비용은 파일 1개 열람 + 검색 1회였습니다.
그리고 넷 다 같은 파일을 지목했습니다 — 게이트였습니다.

한 검증자의 지적이 가장 아팠습니다.

> 이 저장소가 [조용한 실패 5유형](../docs/silent-failure-patterns.md)에서 정의한
> **유형 3(무증상 미수행)** 이 저자의 안전장치에서 그대로 재현됐다.

제가 문서로 정리해둔 실패 유형에 제가 당했습니다.

<br>

## 고친 것

### 게이트 재설계 7가지

| 실패한 설계 | 고친 설계 |
|---|---|
| 금지어를 스크립트에 하드코딩 | 규칙을 **저장소 밖** 파일로 분리 — 경로는 환경변수로 주입 |
| 한 줄에 파이프로 묶인 전체 목록 | **한 행 = 식별자 하나** — 한 번의 열람이 전체 노출이 되지 않게 |
| 자기 자신을 스캔에서 제외 | **검사 도구도 검사 대상** |
| 규칙이 없으면 통과 | 규칙이 없으면 **실패** |
| 적중한 값을 로그에 출력 | **위치만** 출력 — 로그도 유출 경로다 |
| 규칙 파일을 **파일명**으로 식별 | 경로(저장소 안인가)와 **내용**(식별자 목록 형태인가)으로 판정 |
| 작업 트리만 스캔 | **커밋 히스토리 객체까지** 스캔 — 못 보면 통과로 처리하지 않음 |

첫 줄에서 한 번 더 틀렸습니다. 처음 고칠 때 저는 **“추적되지 않는 파일”** 로 옮겼습니다.
`.gitignore` 에 넣었으니 됐다고 본 겁니다. 그런데 `.gitignore` 가 막는 것은 **커밋뿐**입니다.
그 파일은 여전히 저장소 폴더 안에 있었고, 폴더를 zip으로 압축하거나 백업·클라우드 동기화에 걸면
**추적 여부와 무관하게 그대로 따라갑니다.**

고쳤다고 생각한 자리에서 한 번 더 같은 종류로 틀린 것입니다 —
**조치를 했다는 것을 상태가 바뀐 것으로 셌습니다.** 그래서 조건 자체를 고쳐 잡았습니다.

```
✗  「가릴 문자열 전체 목록」은 추적되지 않아야 한다
✓  「가릴 문자열 전체 목록」은 저장소 안에 없어야 한다
```

지금 규칙 파일은 저장소 밖(사용자 설정 디렉터리)에 있고, 경로는 `REDACTION_RULES_FILE` 로 주입합니다.
그리고 게이트가 이 조건을 검사합니다 — 규칙을 문서로만 두지 않고 검사로 만든 것입니다.

**판정 기준을 파일명에서 경로·내용으로 바꿨습니다.** 처음 만든 검사는 `.redaction-rules.local`
**한 이름만** 봤습니다. 그러면 같은 내용을 다른 이름으로 복사해두는 것만으로 검사를 비켜갑니다.
지금은 두 층으로 판정합니다.

| 층 | 판정 | 무엇을 막는가 |
|---|---|---|
| 경로 | 지정된 규칙 파일 경로가 저장소 안이면 **즉시 실패** | 어떤 이름으로 지정해도 통하지 않음 |
| 내용 | 저장소 안에 「분류명 + 패턴」 목록 형태의 파일이 있으면 실패 | 이름을 바꿔 놔두는 우회 |

내용 판정은 이름·확장자·추적 여부를 보지 않고 파일 안의 **형태**를 봅니다.
패턴 칸이 플레이스홀더뿐이면 예시로 인정하고, 리터럴이 하나라도 섞이면 실제 규칙 파일로 봅니다.
그래서 저장소에 남아 있는 예시 파일이 안전한 근거도 위치나 이름이 아니라 **내용 자체**입니다.
CI 는 이 판정을 이름을 바꿔가며(`.local` · `.mine` · `notes.tsv` · `docs/keep.md`) 매번 다시 확인합니다.

두 번째 줄도 같은 사고의 잔재였습니다. 파일을 옮겨도 **한 줄에 파이프로 정렬된 형태**는 그대로였고,
그건 이 케이스 앞부분에서 제가 문제라고 쓴 구조와 정확히 같은 것이었습니다.
지금은 분류별로 **한 행에 식별자 하나**입니다. 게이트는 행마다 독립적으로 검사하므로 탐지력은 동일하고,
추가·삭제·회수는 행 단위로 됩니다.

**「규칙이 없으면 실패」** 도 핵심입니다. 새 환경에서 규칙 파일 없이 돌리면 이렇게 나옵니다.

```
🔴 규칙 파일 없음
❌ 검사 불가 — 통과로 처리하지 않습니다.
```

**“검사할 게 없어서 통과”를 구조적으로 불가능**하게 만들었습니다.

### 히스토리 폐기 — 그리고 폐기했다고 믿었던 것

파일을 고쳐도 **커밋 diff에 원본이 남습니다.**
그래서 히스토리를 버리고 단일 커밋으로 다시 만든 뒤, 원격에 force-push 했습니다.
이걸로 끝났다고 생각했습니다.

**끝이 아니었습니다.**

나중에 로컬 reflog를 다시 읽다가, 버린 커밋들이 `update by push`로 기록돼 있는 걸 봤습니다.
이미 원격에 올라간 적이 있는 커밋이라는 뜻입니다. 확인해봤습니다.

```bash
# 참조는 끊겼지만 객체는 살아 있다
git init && git remote add origin <URL>
git fetch origin <force-push 로 버려진 커밋의 해시>   # → 그대로 내려받아진다
```

**빈 저장소에서 해시만 지정해 fetch 하니 그 커밋이 통째로 내려받아졌습니다.**
안에는 아직 규칙에 등록되지 않았던 식별자가 살아 있었습니다.

force-push가 지운 것은 **브랜치가 가리키는 위치**뿐입니다.
객체 자체는 호스팅 서비스의 GC 정책에 따라 남고, **해시를 아는 사람에게는 계속 제공됩니다.**
그리고 해시는 CI 로그·포크·이벤트 API 어디에나 흘러 있습니다.

| 내가 했다고 믿은 것 | 실제로 일어난 것 |
|---|---|
| 히스토리를 지웠다 | 로컬에 새 히스토리를 만들었다 |
| 원격에서 사라졌다 | 브랜치 참조만 옮겼다 — 객체는 남아 있었다 |
| 되돌렸다 | 되돌아갔는지 **확인하지 않았다** |

로컬에서 히스토리를 버리는 것과 원격에서 객체가 사라지는 것은 **다른 일**입니다.
원격 객체를 확실하게 끊는 방법은 그 저장소를 더 쓰지 않는 것뿐이었고,
그래서 **저장소를 새로 만들었습니다.**

이게 이 케이스의 **두 번째 층**입니다.

### 검사 범위를 공개 범위에 맞췄다

여기까지 고친 뒤에도 게이트는 `git ls-files` 로 **작업 트리만** 훑고 있었습니다.
그런데 이 케이스가 두 번에 걸쳐 확인한 사실이 바로 **작업 트리에서 지운 문자열은 커밋 객체에 남는다**는
것이었습니다. 검사 범위가 공개 범위보다 좁았고, 그래서 오염된 커밋을 그대로 둔 채 초록불이 났습니다.

같은 유형([무증상 미수행](../docs/silent-failure-patterns.md))이 세 번째로 나온 지점이라,
구멍을 하나 더 막는 대신 **불변식을 바꿔** 잡았습니다.

```
✗  작업 트리에 없으면 공개되지 않는다
✓  히스토리 객체에 없어야 공개되지 않는다   ← 검사 범위 = 공개 범위
```

지금 게이트는 `git rev-list --all --objects` 로 도달 가능한 객체를 열거하고,
`git cat-file` 로 블롭 내용까지 **같은 규칙으로** 스캔합니다. 그리고 스캔한 객체 수를 출력합니다 —
"몇 건을 봤는지"가 안 보이면 0건을 봤을 때와 구분이 안 되기 때문입니다.
얕은 클론이면 히스토리 전체를 볼 수 없으므로 통과가 아니라 **실패**로 처리합니다(CI 는 `fetch-depth: 0`).

회귀 검증도 검사로 만들었습니다. CI 가 일회용 클론에 카나리 문자열을 커밋한 뒤 지우고,
**작업 트리가 깨끗한 상태에서** 게이트가 그 문자열을 잡는지 매번 확인합니다.

```
첫 번째 층 — 검사가 "통과"를 출력했다고 안전한 것이 아니다
두 번째 층 — 내가 조치를 했다고 상태가 바뀐 것이 아니다
세 번째 층 — 검사 범위가 공개 범위보다 좁으면, 초록불은 그 범위 안에서만 참이다
```

앞의 둘은 같은 실수의 다른 얼굴입니다. **행위를 결과로 셈하고, 결과를 확인하지 않은 것.**
되돌렸다고 **믿는 것**과 실제로 **되돌아간 것** 사이에는 확인 한 단계가 반드시 있어야 합니다.
세 번째는 거기서 한 칸 더 나간 것입니다 — 확인을 했더라도 **무엇을 확인 대상에 넣었는지**를
같이 봐야 합니다. 그래서 지금은 게이트가 검사 범위를 매 실행마다 스스로 출력합니다.

## 더 큰 배움 — 기준 자체가 틀렸다

게이트를 고치는 것보다 중요한 게 나왔습니다.

원래 기준은 **“이 저장소만 보고 회사를 찾을 수 있는가”** 였습니다.
검증자들이 짚었습니다 — **통과할 수 없는 시험**이라고.

> 이력서에 링크를 붙이는 순간 이름이 공개된다. 이름이 공개되면 소속은 한 다리 건너다.
> 익명을 전제로 한 안전은 처음부터 성립하지 않는다.

맞는 말이었습니다. 그래서 기준을 바꿨습니다.

```
✗  회사를 찾을 수 없게 만든다
✓  회사가 밝혀진 상태로, 그 회사 담당자가 읽어도 문제없는 문장만 남긴다
```

**이 기준이 훨씬 엄격했습니다.** 그리고 기계 게이트가 원리적으로 못 잡는 것들이 걸렸습니다.

| 걸린 것 | 왜 위험한가 |
|---|---|
| 규제 이행 상태 서술 | 회사가 특정되면 **규제기관이 인용 가능한 자료** |
| 손실 사고의 기간·규모 | 경쟁사·고객이 그대로 인용 가능 |
| 현재진행형 취약점의 위치 | 공격 표면을 스스로 공개 |
| 내부 정책의 판정 규칙 | 소비자 관점에서 문제 제기 가능 |

전부 **고유명사가 하나도 없어서** 게이트는 통과했던 문장들입니다.
이 기준을 적용하면서 **케이스 하나를 통째로 삭제**했습니다.

<br>

## 그리고 게이트 통과도 끝이 아니었다

전부 고치고 게이트를 통과시킨 뒤 업로드했습니다.
그다음 **원격에서 다시 clone해서** 대조했더니 **CI 설정 파일에 잔여가 하나** 더 있었습니다.

게이트는 이걸 못 잡았습니다. **그 단어를 규칙에 등록하지 않았기 때문**입니다.

```
게이트는 등록한 것만 본다.
그래서 게이트 통과는 검증의 끝이 아니라 중간 지점이다.
```

이건 [안전 설계 원칙 3](../docs/safety-design.md)과 같은 이야기입니다 —
`200 OK`를 반영으로 믿지 않듯, **“통과”를 안전으로 믿지 않습니다.** 독립 경로로 다시 확인해야 합니다.

<br>

## 이 케이스에서 실제로 배운 것

**안전장치를 만든 사람은 그 안전장치를 검증할 수 없습니다.**

같은 가정 위에서 만들었기 때문에, 그 가정이 틀렸을 때 같이 틀립니다.
저는 게이트를 여러 번 돌려봤고 매번 초록불을 봤고 그래서 안전하다고 믿었습니다.
**검증은 밖에서 와야 했습니다.**

그래서 지금은 순서를 이렇게 잡습니다.

```
1. 안전장치를 만든다
2. 안전장치가 자기 자신을 검사하는지 확인한다
3. 안전장치를 모르는 사람에게 뚫어보라고 시킨다   ← 이게 없으면 1·2는 자기 위안이다
4. 결과에 따라 기준 자체를 의심한다
```

4번까지 갔던 게 이 케이스에서 가장 값진 부분이었습니다.
장치를 고치는 것으로 끝냈다면 **기준이 틀렸다는 건 영영 몰랐을 것**입니다.
