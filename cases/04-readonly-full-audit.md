# 케이스 04 — 읽기전용 전수 감사 + 반증 검증

> 자사몰 전 상품을 읽기 전용으로 훑고, 추출된 지적을 독립 소스로 반증해 3분의 1 남짓으로 압축

**증명하는 역량** · 감사 결과를 그대로 보고하지 않고 **반증한 뒤** 보고. 오탐 패턴을 자산화

<br>

## 문제

안전장치([케이스 02](02-rollback-first-guard.md)) 밖에서 만들어진 과거 잔재는 **표본 점검으로는 절대 발견되지 않는다.**

표본을 아무리 잘 뽑아도, 잔재는 **표본에 안 들어간 곳에** 남아 있습니다.
그래서 전수가 아니면 애초에 답이 안 나오는 종류의 문제였습니다.

그런데 더 큰 문제는 따로 있었다.

> **"이상 없다더니 왜 계속 새로 나오냐"**

감사 자체가 신뢰를 잃고 있었다. 원인은 결함이 아니라 **오탐**이었다.

<br>

## 접근

### ① 전수 + 읽기 전용을 설계 조건으로 고정
```
자사몰 전 상품을 API로 통째 덤프
쓰기 0건 — 감사 도구는 코드 수준에서 쓰기 권한을 갖지 않는다
```
표본으로는 "방치된 잔재"를 원리적으로 못 찾는다. 전수가 아니면 의미가 없다.

### ② 6갈래 병렬 감사
가격 · 옵션 · 상세 · 카피 · 카테고리 · 재고 축으로 나눠 동시 검사 → **지적 목록 추출**

### ③ 지적을 그대로 보고하지 않는다 ← 이 케이스의 핵심
```
지적 목록  →  라이브 API + 고객 화면 실HTML 로 반증  →  **3분의 1 남짓만 생존** (64% 기각)
```
**덤프 인용은 근거가 아니다.** 덤프는 시점 스냅샷이고, 그 사이 이미 고쳐졌거나 애초에 의도된 설정일 수 있다.
지적 하나하나를 **독립 소스로 다시 확인**한 뒤에만 보고했다.

### ④ 텍스트로 못 잡는 유형은 다른 방법으로
이미지 안의 문구는 파일을 직접 내려받아 확인했다. **텍스트 검색으로는 원리적으로 안 잡히는 유형**이 있다는 걸 인정하고 별도 경로를 만들었다.

### ⑤ 오탐을 예외목록으로 자산화
반복 오탐 패턴을 목록화해 다음 감사부터 제외했다.
발견된 오탐 유형 중 하나 — **이미지 인코딩 데이터의 우연한 바이트열이 행사 문구로 오독**되는 경우.

### ⑥ 보고하기 전에 분류 기준을 먼저 세웠다

감사 결과를 세 갈래로 나누는 기준을 정의하고, 반증을 통과한 지적을 그 기준에 따라 배분했다.
```
① 즉시 조치   — 고객 화면에 반영되는 유형
② 조건부 위험 — 평시에는 드러나지 않고 특정 설정이 켜질 때만 발현하는 유형
③ 기각        — 반증되어 결함이 아니라고 판단한 유형
```
①②는 이 순서대로 조치 우선순위가 정해졌고, 승인을 거쳐(⑧) 조치까지 마쳤다.
분류는 보고서 서식이 아니라 **조치 순서를 정하기 위한 장치**였다.
③을 함께 보고하는 것이 중요하다. **무엇을 검사했고 왜 아니라고 판단했는지**가 있어야 감사가 신뢰를 얻는다.

### ⑦ 조치안에 조치 리스크를 병기
```
- 옵션을 통째로 삭제하지 말 것 (물류 매칭이 끊긴다)
- 국가 파라미터 누락 시 반대 시장을 덮어씀
- 상세 수정은 본문 전체 교체이므로 백업 선행
```

### ⑧ 조치는 승인 후에만
감사 도구는 발견까지만 합니다. 무엇을 고칠지는 사람이 정합니다.

<br>

## 결과

| | |
|---|---|
| 감사 범위 | 자사몰 **전 상품** · 쓰기 0건 |
| 지적 압축 | 반증 후 **3분의 1 남짓만 생존** (64% 기각) |
| 조치 | 표본 점검으로는 나오지 않던 과거 잔재 유형을 특정 → **분류 기준에 따라 조치 완료** |
| 부수 효과 | 오탐 패턴을 예외목록으로 자산화 → **감사 신뢰도 회복** |

<br>

## 이 케이스에서 실제로 배운 것

**감사 도구의 품질은 탐지율이 아니라 정밀도로 결정된다.**
오탐이 섞이면 사람은 감사 결과 전체를 안 믿게 되고, 그 순간 진짜 결함도 함께 무시된다.
그래서 **찾는 것보다 기각하는 것에 더 많은 설계를 넣었다.**
