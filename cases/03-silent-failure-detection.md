# 케이스 03 — 에러 없이 멈춘 자동화를 찾아내기

> 스케줄 작업이 실행되지 않는데 실패 로그도 남지 않는 상황을 **탐지 가능한 유형**으로 정의하고, 감시 구조를 설계

**증명하는 역량** · 모니터링의 기본값을 “실패 감시”에서 “부재 감시”로 전환

<br>

## 문제 — 감시할 수 없는 실패의 모양

운영 자동화에서 가장 흔한 장애는 **에러가 아니라 부재**입니다.

- 시스템은 정상으로 보인다
- 에러 로그가 없다
- 모니터링에도 걸리지 않는다 — **실패한 게 아니라 시작조차 하지 않았기 때문에**

실패는 신호를 만들지만 **미실행은 아무 신호도 만들지 않습니다.**
그래서 "실패하면 알려줘"로 설계된 감시 체계는 이 유형을 구조적으로 못 봅니다.

자동화를 늘릴수록 이 문제가 커집니다. 사람이 하던 시절에는 “오늘 그거 안 했네”를 누군가 알아챘는데, 시스템에 넘긴 뒤에는 **돌고 있다고 가정**하기 때문입니다.

미실행이 신호 없이 발생하는 경로는 두 갈래로 갈립니다.

| 유형 | 실체 | 왜 안 보이나 |
|---|---|---|
| **스케줄 등록 이탈** | 설정 플래그·파일명·실행 환경이 바뀌어 실행 대상에서 빠짐 | 실행이 없으니 실패 로그도 없다 |
| **선행 조건 소진** | 처리 대상을 만들어내는 자원이 떨어져 결과가 계속 0건 | 코드는 정상 종료한다 |

두 번째가 특히 까다롭습니다. **0건이 정상인지 이상인지 구분할 기준이 코드 안에 없기 때문**입니다.
"오늘 처리할 게 없었다"와 "처리 자체가 불가능해졌다"가 같은 출력으로 나옵니다.

<br>

## 접근 — 부재를 탐지 가능하게 만든다

### ① 기본값을 뒤집는다 ← 이 케이스의 핵심
```
❌  실패를 감시한다            →  실행이 없으면 실패도 없다
✅  마지막 성공 시각을 감시한다  →  기대 주기를 넘기면 알림
```
작업이 성공할 때마다 타임스탬프를 남기고, **그 타임스탬프의 나이**를 감시합니다.
감시 대상이 "실패 이벤트"에서 "성공의 신선도"로 바뀌면 미실행이 관측 가능해집니다.

### ② 감시자를 감시 대상과 다른 실행 경로에 둔다
같은 스케줄러 위에 올리면 스케줄러가 죽을 때 감시자도 함께 죽습니다.
**하트비트를 보는 쪽이 하트비트를 만드는 쪽과 같은 운명이면 감시가 아닙니다.**

### ③ 0건을 판정 가능하게 만든다
```
❌  "실패하면 알린다"
✅  "정상이어도 처리 건수를 보고한다"  →  0건이 며칠 이어지면 이상
```
"이상 없음"도 출력해야 합니다. 조용히 넘어가면 돌았는지 안 돌았는지 사후에 알 수 없습니다.

### ④ 분모를 정직하게 만든다
처리 대상이 아닌 건을 먼저 분리합니다. 이걸 안 하면 **처리율이라는 숫자가 무슨 뜻인지 알 수 없습니다.**
0%가 "못 했다"인지 "할 게 없었다"인지 분모가 결정합니다.
→ [조용한 실패 유형 3](../docs/silent-failure-patterns.md)

<br>

## 접근 (계속) — 복구 절차도 설계 대상이다

미실행을 발견한 뒤의 소급 처리는 그 자체가 위험한 작업입니다. 절차를 규율이 아니라 순서로 고정했습니다.

### ⑤ 추정 금지 — 규모부터 확정
“대충 몇백 건일 것”으로 시작하면 복구 계획 전체가 틀어집니다. 대상을 전수 조회해 **미처리 규모를 먼저 확정**합니다.

### ⑥ 정상 구간을 먼저 확인해 후보를 소거
어디가 멀쩡한지 아는 것이 어디가 고장인지 아는 것보다 빠를 때가 있습니다.

### ⑦ 암묵지 복원을 공정에 포함
이 유형을 파고들면, 실행에 필요한 선행 절차가 **코드에도 문서에도 남아 있지 않은** 상태를 만나게 됩니다.
과거 기록에서 규칙을 재구성하는 단계가 실제로 가장 오래 걸립니다.
→ [이관 설계](../docs/handoff.md)에서 “설계 결정 기록”을 필수 산출물로 넣은 근거가 여기입니다.

### ⑧ 단계적 확대 + 백업 선행
```
테스트 1건  →  2건  →  전체 백업  →  대상 전량
```
소급 처리는 되돌리기가 특히 어렵습니다. 한 번에 전량을 돌리지 않습니다.

### ⑨ 권한 경계를 절차에 명시
도구는 **사실관계와 선택지까지만** 만듭니다. 후속 처리 방식의 판단은 소관 부서의 결정으로 남깁니다.
**할 수 있는 것과 판단해도 되는 것은 다릅니다.**

<br>

## 결과 ① — 대응은 이렇게 끝났다

| 항목 | 결과 |
|---|---|
| 미처리 대상 소급 처리 | **전량 처리 · 실패 0건** |
| 발견부터 종결까지 | **이틀** |

**실패 0건은 운이 아니라 순서의 결과입니다.** 규모를 먼저 확정했고(⑤), 백업을 쓰기 앞에 뒀고(⑧),
1건 → 2건 → 전량으로 넓혔기 때문에 어느 단계에서 멈춰도 되돌아갈 지점이 남아 있었습니다.
그리고 이틀 중 대부분은 실행이 아니라 **⑦ 암묵지 복원**에 들어갔습니다 — 소급 처리 자체는 짧습니다.

<br>

## 결과 ② — 한 건의 대응으로 끝내지 않았다

이 유형을 **카탈로그로 정리**했습니다.

→ **[조용한 실패 5유형 카탈로그](../docs/silent-failure-patterns.md)**

| 만든 것 | 무엇이 달라지나 |
|---|---|
| 하트비트 감시 (마지막 성공 시각의 나이) | 미실행이 사람 인지에 의존하지 않고 관측된다 |
| 감시자를 별도 실행 경로로 분리 | 스케줄러와 감시가 함께 죽지 않는다 |
| 정상 시에도 처리 건수 보고 | 0건의 의미를 판정할 수 있다 |
| 소급 처리 단계 확대 규칙 | 복구 작업 자체가 2차 사고가 되지 않는다 |
| 배포 전 5문항 체크리스트 | 새 자동화가 같은 유형을 다시 만들지 않는다 |

<br>

## 이 케이스에서 실제로 배운 것

**모니터링의 기본값이 틀려 있습니다.**
우리는 “무언가 잘못되면 알려줘”로 시스템을 만드는데, 운영 자동화에서 가장 흔한 장애는 **아무것도 일어나지 않는 것**입니다.
“아무 일도 없었다”를 이상 신호로 읽을 수 있어야 합니다.
