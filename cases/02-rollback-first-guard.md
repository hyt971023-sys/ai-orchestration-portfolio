# 케이스 02 — 되돌릴 수 없으면 실행하지 않는다

> 대형 변경 전 원본을 통째로 스냅샷하고, 스냅샷이 없으면 실행 자체를 중단하는 배포 가드

**증명하는 역량** · 롤백 경로를 기능이 아니라 **실행 전제조건**으로 설계

<br>

## 문제

대형 프로모션은 라이브 상품의 **8개 필드를 한꺼번에 갈아끼운다** — 상품명, 정가, 판매가, 요약, 상세(PC/모바일 별도), 구매제한, 옵션 표시상태.

종료 시 원복을 하나라도 빠뜨리면 **행사가가 계속 팔리는 손실**이 된다.
그런데 원복 시점에는 담당자가 이미 지쳐 있고, 대상이 수십 건이면 반드시 몇 개를 빠뜨린다.

여기에 눈에 잘 띄지 않는 성질이 두 개 더 겹친다.

1. **스냅샷 범위 밖의 필드** — 백업 목록에 없는 필드는 덮어쓰이는 순간 복원 근거가 사라진다. 옵션 이미지처럼 본문 8개 필드에 안 잡히는 부속 값이 특히 그렇다. **스냅샷의 커버리지가 곧 복원 가능 범위**다.
2. **스왑이 옵션을 재생성하는 계열** — 스왑이 옵션을 *새로 만드는* 동작이면, 옵션 단위에 붙어 있던 판매 차단 설정은 기본값으로 초기화될 수 있다. 단종 처리해둔 조합이 다시 판매 가능 상태로 돌아오는 경로가 여기서 열린다.

두 번째가 특히 위험한 이유는 **에러 없이 일어나기 때문**이다. 요청은 성공하고, 값만 조용히 되돌아간다.
→ [조용한 실패 유형 4 — 조용한 값 리셋](../docs/silent-failure-patterns.md)

<br>

## 접근

### ① 원본을 단일 파일로 통합 저장
8개 필드에 더해 옵션 표시타입·옵션 이미지·색상값까지 하나의 baseline JSON에 넣었다.
흩어져 있으면 복원 시점에 무엇을 빠뜨렸는지 알 수 없다.

### ② 스냅샷 부재 시 실행 중단 ← 이 케이스의 핵심
```python
if product_id not in baseline:
    abort(f"{product_id}: baseline 없음 — 되돌릴 수 없으므로 실행하지 않음")
```
**"백업을 하자"가 아니라 "백업이 없으면 못 하게 한다".**
전자는 규율이고 후자는 구조다. 규율은 바쁠 때 무너진다.

### ③ 복원은 1회 실행으로 전량
복원을 상품별로 하면 반드시 누락된다. 종료 시 **명령 하나로 전 상품 일괄 원복**.

### ④ 복원 실패를 요약하고 종료코드로 알린다
조용히 실패하면 옛 값이 그대로 남는다. → [조용한 실패 유형 3](../docs/silent-failure-patterns.md)

### ⑤ 리셋되는 성질을 전제로 재적용
스왑이 판매상태를 초기화한다는 성질을 **없앨 수 없다면 전제로 삼는다.**
판매금지 목록을 스왑 스크립트에 내장해, 스왑 직후 자동으로 다시 차단하도록 했다.
조합형 옵션이면 그 값이 포함된 **모든 조합**을 차단한다.

### ⑥ 검증을 체인으로 연결
```
원복 → 가격·추가금 감사 → 고객 화면 실HTML 재검증
```
원복했다는 것과 원복이 반영됐다는 것은 다르다.

<br>

## 결과

- 두 시장 **수십 개 상품의 baseline을 한 파일로 관리**
- 원복 누락을 **구조적으로 차단** — 규율이 아니라 가드로 (백업이 없으면 실행 자체가 시작되지 않는다)
- 판매금지 재적용을 **상시 상품 · 이벤트 페이지 · 행사 복사본** — 스왑이 지나가는 전 경로에 자동 적용
- 스냅샷 범위와 재적용 범위를 설계 문서에 명시 → **검증 범위를 그대로 다음 단계 전수 감사의 범위로 인계** (→ [케이스 04](04-readonly-full-audit.md))

<br>

## 이 케이스에서 실제로 배운 것

**보호 범위를 정의할 수 없는 가드는 가드라고 부를 수 없다.**
이 가드에서 시간을 가장 많이 쓴 부분은 차단 로직이 아니라 **무엇이 스냅샷과 재적용의 대상인지 정의하는 일**이었다.
범위가 정의돼 있으면 "검증했다"가 무엇을 검증했다는 뜻인지 말할 수 있고, 그 범위를 다음 단계 감사에 그대로 넘길 수 있다. 정의를 건너뛰면 둘 다 못 한다.
